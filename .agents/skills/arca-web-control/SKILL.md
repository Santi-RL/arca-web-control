# ARCA Web Control

## Preparación

1. Para una operación conocida, leer `references/runtime.md`, `references/credentials.md`, `references/capabilities.md` y `references/job-v2.md`. Consultar `references/commands.md` solo si hace falta una primitiva de diagnóstico.
2. Ejecutar desde la raíz del repositorio y clasificar el pedido como conocido, variante, nuevo o irreversible.
3. Tratar el CUIT como identidad única. Cuando el selector es un nombre, los comandos canónicos consultan primero el índice no secreto, antes de crear jobs, logs, workers o Chrome. Un nombre exacto puede usarse si identifica un único CUIT; ante un typo, orden invertido o un único segundo nombre omitido, mostrar nombre y CUIT de los candidatos y exigir confirmación humana aunque exista uno solo. Nunca cargar la clave ni iniciar sesión a partir de una sugerencia. En el selector de representado, priorizar un control que contenga el CUIT exacto y luego el nombre completo sin importar el orden. Solo si ninguno aparece, admitir que el nombre guardado y el nombre canónico asociado por ARCA al CUIT exacto difieran en un único segundo nombre o apellido completo; el control accionable debe coincidir exactamente con ese nombre canónico y ser único. No usar distancia de edición, coincidencias parciales ni esta tolerancia sin el CUIT visible.
4. Respetar el proveedor elegido por el usuario. No exigir el Administrador de credenciales de Windows, no repetir una clave en la respuesta y no trasladarla a argumentos, logs, Git o artefactos fiscales.

## Operación

- Antes de abrir Chrome, completar un único preflight conversacional. Si faltan datos obligatorios, pedirlos juntos en un solo mensaje: emisor, tipo de receptor, CUIT cuando corresponda, condición frente al IVA, punto de venta, fecha, período, condición de venta, descripción e importe. No preguntar de a uno ni exigir centavos explícitos; el vencimiento puede quedar predeterminado. El concepto fiscal de esta capacidad es siempre `Servicios`: cuando el usuario llama «concepto» al texto libre, tratarlo como `description` y no cambiar el concepto fiscal.
- Para una factura cuyos datos llegan por chat, generar un UUID privado `intentId` para esa solicitud y usar una sola invocación a `arca:invoice:prepare-chat` con JSON por `stdin`. Reutilizar ese UUID únicamente al reconstruir o reintentar la misma intención; una factura nueva, aunque tenga datos idénticos, recibe otro. Esta ruta valida y normaliza datos, resuelve el emisor una vez, crea o reutiliza el mismo job idempotente, inicia o reutiliza Chrome visible y devuelve el resumen; no copiar handles ni `intentId` internos en la conversación. Para las capacidades operativas promovidas, usar siempre la sesión visible normal: no agregar `--revalidate-irreversible`. Si el emisor resuelto difiere del de la sesión visible anterior, el nuevo pedido constituye la instrucción explícita de relevo: `prepare-chat` cierra esa sesión de forma controlada y abre la nueva sin pedir otra autorización. Solo debe detenerse si la sesión anterior está procesando un comando, no puede probarse viva o presenta un estado incierto que impida el cierre controlado.
- Si solo hace falta identificar al emisor antes de completar el intake, usar `arca:issuer:resolve`. Una falta de coincidencia debe devolverse inmediatamente desde el índice local: no abrir Chrome, iniciar aprendizaje, inspeccionar logs ni recorrer el repositorio. `arca:credentials:list` puede mostrar el índice completo cuando el usuario lo pida; nombre y CUIT no se tratan como claves.
- Usar `arca:session:start`, `arca:job:create` y `arca:session:cmd` como primitivas de diagnóstico o recuperación, no como preámbulo obligatorio del flujo conversacional normal.
- Navegar incrementalmente desde la pantalla actual. No reiniciar, volver al portal ni abrir una URL directa salvo pedido explícito; solicitar una factura con otro emisor ya es un pedido explícito de cambio de sesión.
- Para una capacidad nueva o variante, usar `arca:learn:start`; comenzar el registro después del login y detenerse antes de toda acción irreversible.
- Mantener eventos, notas, capturas y `candidate.json` exclusivamente en `%LOCALAPPDATA%\ManejoARCA\learning`. Nunca incorporarlos directamente a Git ni adjuntarlos a un issue o PR.
- En aprendizaje híbrido, ejecutar `inspect` antes de cada mutación y usar su `inspectionId` de un solo uso con `click-exact`, `select-exact`, `fill-input`, `check-exact` o `press`. Si hay varias pestañas ARCA, `inspect <índice-pestaña>` exige elegir una explícitamente y liga la inspección a esa página. Ignorar y no registrar pestañas de otros orígenes. Solo mutar pantallas ARCA conocidas previas al resumen. Las pantallas nuevas requieren interacción manual y los valores de `fill-input` llegan por stdin, nunca por argumentos.
- Si aparece captcha, selector ambiguo, control inesperado o pantalla no documentada, detenerse y pedir intervención humana.
- Si una sesión visible queda pausada por captcha, no reenviar el login en el mismo aviso. Después de que el usuario confirme que intervino, ejecutar explícitamente `arca:session:cmd -- resume-authentication` en una sesión operativa o `arca:learn:cmd -- resume-authentication` en un aprendizaje, siempre sobre el mismo Chrome. Si el captcha continúa o la pantalla no es el login oficial esperado, volver a detenerse. Una credencial rechazada clausura toda reanudación posterior y detiene ese worker sin un segundo intento.
- Ante `ARCA_INVALID_CREDENTIALS`, informar y detenerse sin un segundo intento.
- Ante `403 Forbidden` o `TU SESIÓN HA EXPIRADO` antes del primer clic irreversible, no reenviar el formulario: finalizar el tramo, autenticar nuevamente y reconstruir el borrador con el mismo `intentId`. Si ocurre después del clic, prevalece `unknown`: no reconstruir ni reemitir y reconciliar primero.
- No improvisar selectores ni usar coincidencias parciales en producción.

## Facturas

1. Usar `invoice-services-single-item` únicamente para un receptor identificado por CUIT. Tratar el Consumidor Final sin identificar como la capacidad separada `invoice-services-single-item-consumidor-final-anonimo`. Ambas tienen emisión visible controlada, se limitan a Factura C, concepto Servicios, moneda local y un ítem y prohíben el modo oculto; cualquier otra variante debe pasar por aprendizaje visible.
2. Exigir datos completos mediante el preflight único. La entrada conversacional acepta fechas `DD/MM/AAAA` o ISO, importes enteros como `1.500.000`, importes argentinos con centavos o decimal canónico y vencimiento `Default`; el motor normaliza también `Responsable Inscripto` a `IVA Responsable Inscripto` antes de abrir Chrome. No inferir otras condiciones fiscales a partir de abreviaturas desconocidas.
3. Seleccionar el punto de venta exacto solicitado y, aunque otros puntos compartan domicilio, esperar e inspeccionar el selector dependiente de tipo de comprobante. Exigir exactamente una opción habilitada `Factura C`, seleccionarla y releer ambos valores. Si no está disponible, está duplicada o el selector es ambiguo, mostrar las opciones visibles y detenerse.
4. Ejecutar `arca:invoice:prepare-chat`, conservar el `preparedInvoiceId` devuelto y mantener la misma sesión visible hasta terminar o detener la operación. No cerrar, cambiar de carril ni volver a cargar la factura después del resumen.
5. Validar el receptor según `references/job-v2.md`. Para el receptor identificado, el CUIT exacto es la identidad fuerte. `recipientName` es una expectativa legal opcional: usarlo solo cuando el usuario haya dado una razón social completa que deba verificarse; no convertir una abreviatura o apodo comercial en una expectativa bloqueante. Si se omite, ARCA debe devolver un único nombre legal no vacío asociado al CUIT y ese nombre pasa al resumen verificado. Si una expectativa no coincide y aparece `ARCA_RECIPIENT_NAME_CONFIRMATION_REQUIRED`, mostrar al usuario el nombre canónico y el CUIT incluidos en el error y pedir una confirmación concreta; no pedirle que adivine el nombre. Para el receptor anónimo, exigir `recipientKind: "anonymous-final-consumer"` e IVA `Consumidor Final`; después de seleccionar esa condición, esperar la carga del selector de tipo de documento y releerlo sin tocarlo ni disparar `change`. Debe existir un único tipo visible y habilitado, `CUIT`, ya preseleccionado por ARCA. Un default distinto, vacío, duplicado o deshabilitado es una variante y bloquea. Verificar además que número de documento, nombre y domicilio estén vacíos y que el resumen mantenga sin valor CUIT, razón social y domicilio; nunca inferir esta variante por datos faltantes. En cada página o copia del PDF, la fila del receptor anónimo admite exactamente dos representaciones: una única etiqueta `CUIT` sin valor en la misma fila de `Razón Social` vacía y sin prefijo adicional, o la ausencia de esa etiqueta acompañada obligatoriamente por el marcador exacto `Doc.: -` inmediatamente antes de `Razón Social`. Una fila sin ninguno de los dos marcadores o con otro tipo o valor documental bloquea. Cualquiera de las dos representaciones solo es válida si razón social y domicilio permanecen vacíos, la condición frente al IVA es `Consumidor Final`, el bloque del receptor es único y contiguo y el único CUIT no vacío corresponde al emisor. El mismo CUIT emisor puede repetirse una vez por copia como la misma identidad; dentro de una página se bloquean etiquetas duplicadas en un mismo rol o sección y cualquier CUIT adicional. En ambas capacidades, `Email` y `Comprobantes Asociados` son optativos pero sus valores no forman parte del contrato vigente: no completarlos, exigir evidencia visible de que el email y todos los campos de comprobantes asociados permanecen vacíos, y verificar que el resumen represente `Email` sin valor y `Comprobantes Asociados` con `-`. Si el usuario solicita completar alguno, tratarlo como una variante aún no modelada ni aprendida; nunca inferir su contenido. Mostrar emisor, CUIT del emisor, punto de venta, tipo, concepto, moneda, fecha, período, vencimiento, receptor, CUIT o ausencia de identificación, condición frente al IVA, domicilio o ausencia declarada, condición de venta, descripción, cantidad, precio unitario, subtotal y total. Para un receptor identificado, encabezar la confirmación con `Receptor: <nombre legal devuelto por ARCA> — CUIT <CUIT formateado>`; el usuario debe ver esa identidad antes de autorizar. No inferir ningún dato del resumen: todos deben provenir de la salida estructurada verificada.
6. Para un receptor identificado cuyo domicilio no fue indicado, aceptar automáticamente solo cuando ARCA devuelva exactamente uno. Ante dos o más, no elegir el primero ni el predeterminado: mostrar las opciones y detenerse hasta recibir una selección explícita. Después de recibirla, conservar `intentId`, incrementar `intentRevision` y reconstruir el borrador; esta revisión solo se admite antes del primer clic irreversible y sobre un ledger `failed_before_emit` o una preparación huérfana.
7. Presentar el resumen completo y detenerse. Un consentimiento previo, `sí`, una paráfrasis o un mensaje que además contenga otras palabras no autorizan la emisión. Solo después de recibir un mensaje humano nuevo exactamente igual a `EMITIR`, ejecutar una única vez `emit-prepared-invoice <preparedInvoiceId> EMITIR` sobre la misma sesión y preparación. No volver a autenticar, reconstruir ni recargar entre el resumen y esa orden mientras la sesión siga vigente.
8. El carril `--revalidate-irreversible` pertenece al modo validación controlada y no al modo operativo. Solo sirve para certificar una versión cuyo manifiesto esté explícitamente pendiente. En ese caso excepcional, si la intención autorizada es validar una emisión real, usar la capacidad exacta y entrar en ese carril desde la primera invocación de `arca:invoice:prepare-chat`; nunca preparar primero en la sesión normal y luego reconstruir en otra. Después del resumen y de un mensaje humano nuevo exactamente igual a `EMITIR`, ejecutar una sola vez `revalidate-prepared-invoice <preparedInvoiceId> EMITIR`. Una capacidad ya validada o promovida no puede usar este carril. Antes del primer clic se reservan el ledger y una atestación ligada a la versión; desde el primer intento de clic, cualquier timeout, desconexión, caída o resultado incierto queda —o se recupera como— `unknown` y nunca habilita un reintento automático.
9. Toda emisión debe comprobar que, después de `Comprobante Generado`, exista exactamente un `Imprimir...`, que el listener se instale antes de su único clic, que se capture y valide la descarga directa y que se extraigan número/CAE antes de marcar `emitted`. Si el PDF contiene varias páginas o copias, validar todas por separado contra el job, exigir exactamente una ocurrencia etiquetada de número de comprobante y una de CAE por página y comprobar que ambos valores y los demás datos fiscales coincidan entre todas; la falla o discrepancia de una sola mantiene `unknown`. Ante ausencia, ambigüedad o falla, no abrir una URL alternativa ni repetir el clic.
10. Publicar el PDF y su JSON de metadatos únicamente después de validarlos, bajo `downloads\Emisores\<CUIT formateado - nombre>\Comprobantes Emitidos\<AAAA>\<MM>`. Usar el CUIT como identidad, reutilizar una única carpeta existente y bloquear duplicados o colisiones; nunca sobrescribir.
11. Para Servicios, calcular el vencimiento cinco días corridos desde el campo `date` del comprobante si el usuario no indica otro; dejar actividad, referencia comercial y unidad de medida sin selección por defecto. Si ARCA normaliza la unidad a `unidades` en el resumen, verificarla como salida del portal.
12. Leer `docs/regimenes-especificos.md` antes de informar una actividad asociada. Si el job declara un régimen específico, exigir que régimen y actividad coincidan con el perfil privado del CUIT emisor; los jobs v2 históricos con `activity` explícita siguen siendo compatibles.

## Rendimiento y mantenimiento

- La resolución por nombre es un único preflight local. `arca:invoice:prepare-chat` y `arca:learn:start` ya lo incorporan; no duplicarlo en el camino normal. Ante una sugerencia, mostrarla y esperar confirmación en lugar de encadenar diagnósticos. Un nombre ausente o aproximado no debe crear logs, worker ni Chrome.
- No ejecutar tareas de desarrollo, validación de repositorio ni mantenimiento durante una factura rutinaria.
- El arranque normal solo valida límites administrados del runtime y nunca enumera carpetas históricas desconocidas.
- Al adoptar una versión nueva del layout sobre un runtime existente, el marcador privado obliga a ejecutar una única vez `arca:runtime:repair` antes de operar. Los arranques siguientes vuelven al camino O(1).
- Usar `arca:runtime:repair` únicamente como mantenimiento explícito, fuera de una sesión fiscal y con su confirmación literal. El comando bloquea la reparación si detecta una sesión o aprendizaje vivos o si no puede verificar sus indicadores privados.
- Medir por separado login a resumen (`chat_login_to_summary`) y confirmación a PDF guardado en staging privado (`emission_confirmation_to_pdf`) durante las corridas operativas usadas para evaluar rendimiento.

## Aprendizaje durable

`finish` produce únicamente un candidato privado. No convertir una observación real en capacidad productiva de forma automática: generalizarla en un flujo Playwright rígido, fixtures ficticios, pruebas, manifiesto, recuperación y documentación sanitizada, y exigir una validación humana visible separada.

No habilitar `production-hidden` salvo que el manifiesto declare simultáneamente `maturity: fast_path` y `hiddenAllowed: true` después de validación humana real.
